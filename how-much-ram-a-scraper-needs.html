Sizing

How much RAM a scraper needs before it dies

Most scraping jobs do not need much memory. The ones that die overnight usually die from one specific habit, and it looks like a network problem right up until you watch the process.

The four things that consume memory

  1. The page itself. A rendered product page with images can be 100–400 MB in a real browser. Multiply that by your concurrency and you have your floor.
  2. The browser, not your script. A headless Chrome instance has a fixed cost of roughly 150–300 MB before it loads anything. Five parallel browsers is 1 GB gone before your code runs.
  3. Buffers. Reading whole responses into memory, holding CSV or JSON in a list, keeping every result until the end. All invisible until the job is large.
  4. Leaks you did not write. Libraries and drivers leak too — especially long-lived browser contexts that are never recycled.

The failure that looks like the network

Memory pressure rarely announces itself. What you observe instead:

  • Requests start timing out — but the network is fine and everything is slow.
  • The job works for 40 minutes and then "the site started blocking us".
  • The process disappears with no traceback, or the OS kills it silently.
  • Throughput decays gradually instead of dropping off a cliff.

All four are the same story: the box began swapping, everything got slow, and the first thing you blamed was the network. Watch free memory across the whole run, not just at the start.

How to size it properly

  1. Measure, don't guess. Log RSS for the process and for each browser instance every minute for a full run. The peak matters, not the average.
  2. Recycle aggressively. Restart browser contexts every N pages. It costs a second and removes most long-run growth.
  3. Stream results to disk. Never hold the full dataset in memory; write as you go.
  4. Cap concurrency by memory, not by ambition. If one browser costs 250 MB and you need 4 GB for the OS, that is your ceiling.
  5. Leave headroom. Running at 90% memory means the first traffic spike puts you into swap, and swap turns a fast job into a slow one before it turns it into a dead one.

Why a bigger box is not always the answer

If memory grows linearly with pages processed, more RAM only delays the crash. Fix the growth first — recycling, streaming, capping — and then size the machine for the corrected profile. Hosts that let you resize without rebuilding make this cheap to test, which is one reason we look for RDP and VPS plans that can be moved between tiers in place rather than migrated by hand.

Short version

  • Browsers, not your script, set the memory floor: 150–300 MB each before any page loads.
  • Memory pressure shows up as timeouts and "blocking", not as an out-of-memory message.
  • Log peak RSS for a full run; recycle contexts; stream results to disk.
  • Fix growth before buying RAM, or you only delay the same crash.
