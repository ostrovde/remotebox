Formulas, so you can check the maths:
pages in flight = workers × pages per worker
process overhead = workers × per-browser cost (from the first field)
page memory = pages in flight × page weight × overhead factor
peak = (OS base + process overhead + page memory) × (1 + margin ÷ 100)
plan = smallest of 1 / 2 / 4 / 8 / 16 / 32 / 64 GB that leaves 20% free

What the model says in practice

  • Workers matter more than page weight. Each browser instance carries a fixed cost before it loads anything, so going from 2 workers to 6 adds most of a gigabyte regardless of content.
  • Pages in flight is the line people forget. Four workers with three open pages each is twelve rendered documents in memory at once, not four.
  • If the estimate surprises you, cut pages in flight before cutting workers. It reduces memory more per unit of throughput lost.
  • No browser at all is a different budget entirely. HTTP-only fetching is roughly an order of magnitude lighter — worth checking whether the target actually needs rendering.

Sizing after the estimate

Use the number as the floor, then confirm against a real run: peak RSS over a full cycle, not the average. If real usage keeps climbing past the estimate, you have growth that a bigger plan will only postpone — recycle browser contexts and stream results to disk first. Hosts that let you move between plan sizes without rebuilding make this iteration cheap, which is one reason we look for plans that resize in place rather than requiring a manual migration.

Estimates only. The tool makes no network requests: everything is computed in your browser and nothing is sent anywhere.
